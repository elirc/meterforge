# Review 6: diagnose without inventing certainty

Use this guide for the usage and rating casebooks. The scenarios are fictional teaching cases grounded in local source. A strong answer separates the supplied observation, the source-supported explanation and the additional evidence needed to decide between alternatives.

## Usage case A

Whitespace around meter and external ID, decimal scale differences and equivalent timestamp offsets can normalize to the same payload. Replay is therefore consistent with the current service. Verify subscription and tenant as well; the highlighted fields are not the entire equivalence relation. The operator explanation should say the retry represents the same normalized event, rather than saying changed input is always ignored.

## Usage case B

Padded tenant strings can produce distinct current keys even if a dashboard trims them for display. Request structured identity evidence and lengths, scoped to the incident. The source supports the possibility, but actual request evidence is needed to establish that it occurred. A normalization fix needs collision handling for existing records.

## Usage case C

A lost response does not prove that the first event was not stored. A corrected quantity under the same key can conflict with the original winner. Recovery and correction are separate operations. The safe next step is an authorized identity-based observation through an existing or proposed recovery interface, followed by a defined correction policy if needed.

## Usage case D

The equivalent 64-call wave in the studio observes one event identity and one original-acceptance flag. Its scope is the in-memory implementation. For a mixed-payload wave, either payload family may win, but incompatible candidates must not both become accepted content under the same key. Durable restart behavior remains outside this experiment.

## Rating cases

The one-cent difference follows from the rounding point: one product of 0.01 versus two products of 0.005 each rounded to zero. The incomplete-coverage case follows from a finite last tier that ends before the requested quantity. Neither explanation requires assuming binary floating-point error.

Negative Money values are representable while negative Invoice lines are rejected. A numeric three-character currency code can pass the local constructor but does not establish real settlement support. Reordered distinct valid tiers preserve the sorted schedule; duplicate or ambiguous bounds require separate analysis.

## Remediation structure

Divide a remediation note into future prevention, current incident resolution and historical review. A catalog validator can prevent incomplete schedules going forward. Recalculating a disputed invoice requires the exact historical schedule and rounding policy. Auditing earlier invoices requires stored evidence sufficient to identify the affected population.

A proposed stronger rule should include migration implications. Normalizing tenants may merge keys. Changing rounding may alter totals. Enforcing supported currencies may affect historical document loading. Preventing new errors is valuable, but it does not automatically repair or explain old data.

## Communication check

A useful operator note names the last confirmed effect and the next observation. It should not instruct blind retry when the durable result is unknown. It should not call a source hypothesis a confirmed incident cause. It should not bury the required action beneath a long inventory of implementation details.

Ask the learner to write one note for response loss and one for a rounding dispute. Each should fit a short paragraph while preserving the key distinction. For response loss, distinguish client timeout from stored outcome. For rounding, identify schedule version and rounding boundary as the evidence needed for comparison.

## Review completion

The learner passes when every case has a concrete next step and at least one alternative explanation or missing observation. They should be able to say what would disprove their initial hypothesis. That habit makes the casebook useful beyond these examples because it teaches evidence-driven diagnosis rather than memorized error labels.
