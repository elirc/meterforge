# M4 — reference answer

**Generated SQL (EF Core 10.0.12, SQL Server provider). Shapes to expect:**
- `GetAsync` with `Include(Lines)`: one `SELECT` from a subquery `TOP(2)` over `invoices` (because of `SingleOrDefault`), `LEFT JOIN invoice_lines`, `ORDER BY` invoice keys. Every line row repeats the invoice columns.
- Dedupe lookup: `SELECT TOP(1) ... FROM billing.usage_events WHERE tenant_id = @tenantId AND external_event_id = @externalEventId`, with parameters typed `varchar(64)` and `varchar(128)` (EF uses the column's mapping; this is why the EF path seeks, and the raw SQL in incident 003 didn't).
- Summary: `SELECT subscription_id, meter, COALESCE(SUM(quantity), 0.0), COUNT(*) ... WHERE tenant_id = 'literal' AND occurred_at >= @from AND occurred_at < @to GROUP BY subscription_id, meter`.

**Include vs AsSplitQuery for 1 invoice × 2,000 lines.** Single query: 2,000 rows, each carrying the invoice's 7 columns (small here). The cartesian explosion only bites with **two or more** sibling collections (lines × payments × credits multiply). With one collection, a single query is usually as fast or faster (one round trip). Split query: 2 round trips, the second `SELECT invoice_lines ... INNER JOIN (the invoice subquery) ORDER BY ...`. Risk: without a transaction (or snapshot isolation), a line added between the two queries makes the result inconsistent; for **finalized, immutable** invoices that risk is nil, for drafts it's real. Verdict for MeterForge: keep the single query; switch to split only if more collections are added. Configure globally with `UseQuerySplittingBehavior` only after measuring.

**Tracking vs no-tracking.** Tracking builds a snapshot of every property for change detection and puts the entity in the identity map: ~2× allocations on this tiny row. The break: `AddAsync` adds a **new** `UsageEventRow` for the same `(tenant, external_event_id)` only when the lookup returned null, so no conflict there, but in the batch ingestor of incident 002 (same context, loop), a tracked lookup of an already-added row followed by another `Add` would throw "another instance with the same key is already being tracked" (key = `Seq`, which is 0 until saved). Tracking is correct when you load in order to modify and `SaveChanges`.

**Compiled query.**
```csharp
private static readonly Func<MeterForgeDbContext, string, string, CancellationToken, Task<UsageEventRow?>> Dedupe =
    EF.CompileAsyncQuery((MeterForgeDbContext db, string tenant, string external, CancellationToken ct) =>
        db.UsageEvents.AsNoTracking().FirstOrDefault(e => e.TenantId == tenant && e.ExternalEventId == external));
```
It skips expression-tree hashing and query-cache lookup (the LINQ → SQL translation is already cached by EF after the first run). Typical measured gain on this query: a few microseconds per call, a few percent at most; worth it only on the hottest path (400 calls/s), and it costs readability. The database round trip dominates.

**Surprises worth writing down (any one).** `string.Equals(a, b, StringComparison.Ordinal)` isn't translatable; `==` translates to SQL `=` and **inherits the column collation** (case-insensitive by default!). `DateOnly.FromDateTime(e.OccurredAt.DateTime)` translates to a `CAST` that uses the **local** part of the offset. `GroupBy(...).Select(g => g.First())` became translatable only in recent EF versions and produces a `ROW_NUMBER()` subquery.

**Rubric.** Pass = SQL pasted for all 3 + a measured (not quoted) number for split vs single and tracking vs not + the "`==` inherits collation" insight or equivalent.
