**Explain-before-touching**
1. Locking READ COMMITTED: `SummarizeAsync` takes short-lived **S** locks on each row/page it reads and releases them as it moves on. It blocks
   when it reaches a row the rollup's `UPDATE` holds **X** (claimed but not committed); rows in the reader's tenant and period that the job claims
   in the same transaction block the reader until the job commits. With a 50k-row claim + `MERGE`, that can be seconds.
2. RCSI: readers see the last committed version (version store in `tempdb`, 14-byte version tag per modified row). Costs: `tempdb` space and
   I/O, longer version chains during long transactions, and a new anomaly: a reader can see "before" data while a writer has already changed
   it (fine for the usage page; dangerous for any "read, decide, write" logic that relied on blocking reads).
3. `MERGE ... WITH (HOLDLOCK)`: without serializable range locks, two concurrent `MERGE`s for the same new key can both see "not matched"
   and both `INSERT` → PK violation (or duplicates without a PK). `HOLDLOCK` locks the key range so the second waits.
4. `UPDATE TOP (50000)` acquires row locks; after ~5,000 locks on the table in one statement SQL Server tries to **escalate** to a table
   (or partition) lock. An X table lock blocks every insert from the writers and every locking read until the job commits.

**Expected observations**
- RCSI OFF, soak running: Part A shows summary sessions with `LCK_M_S` waiting on the job's session (`wait_resource` = `KEY: ...` on
  `PK_usage_events`), and writers with `LCK_M_IX` waiting if escalation happened. Summary p50 stays low, max spikes to the job's duration.
- RCSI ON: summary latency no longer depends on the job (no `LCK_M_S`). Writers vs job unchanged: both still take X/U locks.
- Hand-made deadlock (two sqlcmd sessions):
  ```sql
  -- session 1                                           -- session 2
  BEGIN TRAN;                                            BEGIN TRAN;
  INSERT billing.usage_events (...) VALUES (... 'evt_dl_1' ...);
                                                         UPDATE billing.usage_daily_rollups SET event_count += 1
                                                          WHERE tenant_id = 'tenant-0001' AND ...;   -- row R
  UPDATE billing.usage_daily_rollups SET event_count += 1
   WHERE tenant_id = 'tenant-0001' AND ...;  -- waits for 2
                                                         UPDATE billing.usage_events SET rolled_up = 1
                                                          WHERE tenant_id = 'tenant-0001' AND external_event_id = 'evt_dl_1';  -- waits for 1 → deadlock
  ```
  Graph labels: victim = the session with less log to roll back; process A owns `KEY` on `PK_usage_events` (X, the inserted row), waits for
  `KEY` on `PK_usage_daily_rollups` (U/X); process B the reverse.

**Recommendation.** Batch ≤ 4,000 rows (below escalation), loop until fewer than a batch is claimed; lock order rule "`usage_events` before
`usage_daily_rollups`, everywhere"; keep `HOLDLOCK` on the `MERGE` (or split into `UPDATE` + `INSERT ... WHERE NOT EXISTS` under `UPDLOCK, HOLDLOCK`);
add `READPAST` on the claim so the job skips rows writers are still inserting; turn RCSI on for the reader side after a review of read-then-write code.
