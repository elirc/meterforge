# Sealed notes for navigation/TRADEOFFS.md

**T1 — producer key dedupe.** Trade-offs: A puts the burden on SDKs to generate stable keys, and gives exact dedupe forever (as long as keys are retained); B dedupes legitimately identical events (two real calls in the same millisecond with the same quantity) = under-billing; C covers any endpoint, but needs a response store and a TTL, after which retries double-bill. Choice: A, with the key opaque and **case-sensitive** end to end (trim policy decided once, at the boundary). Failure modes: normalization mismatch (review finding 2), collation (incident 004), retention of keys shorter than the SDK retry window. Tests: replay, case, whitespace, concurrency (two deliveries). Monitor: replay rate per tenant (sudden rise = SDK retry storm; sudden drop to 0 while traffic is flat = dedupe broken), 2601/2627 counts. Revisit: if producers can't supply stable keys (e.g. a batch file import): then hash-of-line-in-file becomes the key.

**T2 — identity clustered + GUID unique.** A: simplest, EF default, but random inserts, 16-byte clustering key in every nonclustered index, fragmentation. B (chosen): append-only inserts, 8-byte key, and a second unique index that still takes random inserts. C: best for tenant/time reads (range scans without lookups), but inserts land in ~N tenant "hot spots": fine for many tenants, bad for a whale; wider key everywhere. D: removes most of B's second-index cost if ids are generated sequentially (UUIDv7 in .NET 9+: `Guid.CreateVersion7()`). Failure mode of B: last-page insert contention (`PAGELATCH_EX`) at very high insert rates; mitigations `OPTIMIZE_FOR_SEQUENTIAL_KEY = ON` (SQL 2019+). Monitor: `PAGELATCH_EX` waits, index fragmentation of `ux_usage_events_id`. Revisit: > 10k inserts/s or when reads by `(tenant, time)` dominate.

**T3 — Money with 2 decimals.** A (chosen): invariants in one place, rounding explicit at each step (`TieredRater` per tier, `PercentageDiscount.Apply`). B: no rounding ambiguity at all in storage, but every rate and ratio still needs rounding rules, and APIs must convert. C: exact until finalization, but every intermediate store must have enough scale (`decimal(28,10)`), and the "one rounding" point must truly be single. Failure modes: persistence precision lower than the domain (EF's `decimal(18,2)` default, and SqlClient **truncating** extra scale instead of rounding: incident 005), per-line vs per-total rounding disagreements with the payment provider. Tests: property test "sum of rounded lines = rounded total within ±n×0.005", round-trip tests against the real database. Monitor: reconciliation `amount_mismatch` rate by cents. Revisit: multi-currency with 0- or 3-decimal currencies (JPY, KWD): Money's hardcoded 2 breaks.

**T4 — ports + in-memory defaults.** A (the intent): fast domain tests and honest adapter tests; requires discipline to actually run contract tests against real engines. B: tests pass while the real provider behaves differently (collation, precision, unique indexes: see J3). C: slower CI (container start ~20–40 s), but it's the only thing that proves the adapter. Failure mode seen here: the Postgres adapter was never wired or tested, and readiness claims it's available. Monitor: readiness must report the **actual** store and check connectivity. Revisit: now; any durable adapter needs one contract-test suite that runs against both in-memory and real stores.

**T5 — rollup batch job.** A (chosen in the lab): ingestion stays one short insert; totals lag by one job interval; needs locking discipline (claim first, events → rollups order, batches below escalation). B: always-fresh totals, but every ingest now updates a hot row (one row per subscription/meter/day = hot-row contention for whales) and creates the lock-order cycle with the job (incident 002 family). C: indexed view is maintained synchronously by SQL Server inside each insert = same hot-row contention as B, plus restrictions (`SCHEMABINDING`, `COUNT_BIG(*)`, deterministic expressions only; grouping by `CAST(occurred_at AS date)` means grouping by the **local** date of each offset, which is a billing-day bug unless all offsets are +00:00). D: scalable, but a new system to operate. Late events: A handles them naturally (claimed on the next run) as long as invoicing closes a period only after a lateness window. Revisit: if the usage page must be real-time.
