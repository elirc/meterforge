# S1 — reference design: Postgres → Azure SQL, zero downtime, with rollback

**1. Target schema.** Keep: clustered `seq` identity for `usage_events` (append-only), BIN2 (or `Latin1_General_100_CS_AS_SC_UTF8` with `varchar`) on every opaque key (`external_event_id`, and decide explicitly for `tenant_id`, `meter`, product `code`), `datetimeoffset` for instants, `decimal(19,4)` quantities, `decimal(19,2)` money, JSON in `nvarchar(max)` + `ISJSON` (Azure SQL has a native `json` type; adopt it later as a separate change). Change: compat level 160 **after** a Query Store baseline at 150 (PSP optimization changes plans); plan for RCSI **on** (Azure SQL default): readers stop blocking on the rollup job, `tempdb`/version-store cost; review every "read then write" that relied on locking reads (the dedupe lookup is protected by the unique index, not by locking, so it's fine). Tier: Business Critical or Hyperscale for the 3,000/s peak with log rate headroom; measure log MB/s during backfill.

**2. Data movement per table type.**
- `usage_events` (append-only, 1.2B rows): bulk backfill by `seq`/`occurred_at` ranges (idempotent: `INSERT ... WHERE NOT EXISTS` on `(tenant_id, external_event_id)`, or a staging table + `MERGE`), throttled on log rate; then CDC (Debezium on Postgres logical replication → Azure SQL sink) or app **dual-write** for new events. Because events are immutable and keyed by `(tenant, external_event_id)`, replay is safe: duplicates are rejected by the unique index.
- `invoices`/`invoice_lines` (immutable once finalized): backfill + CDC; verify per-invoice checksums.
- `outbox_messages` (mutable `published_at`): don't migrate in-flight rows; drain the publisher on Postgres before write cut-over, start a new publisher on Azure SQL.

**3. Cut-over sequence (each step gated).**
1. Schema on Azure SQL via EF migrations (`dotnet ef migrations script --idempotent`, reviewed). Gate: script reviewed for collation/precision.
2. Backfill history. Gate: per-tenant per-day `SUM(quantity)`/`COUNT` match for all days.
3. Start CDC. Gate: lag < 5 s at peak for a week.
4. Shadow reads: the usage page reads both, compares, serves Postgres (flag `usage.read_source=pg`, log diffs). Gate: zero diffs for 3 days incl. an end-of-hour peak.
5. Flip reads to Azure SQL (flag). Gate: p95 and error rate unchanged for 48 h.
6. Flip writes: stop CDC direction PG→Azure, start **reverse** CDC Azure→PG (for rollback), switch the ingest write path (flag). Brief window: pause ingestion for seconds with SDK back-pressure (503 + `Retry-After`; SDKs retry for 24 h, dedupe absorbs duplicates), or dual-write with Azure SQL as primary.
7. Run one invoicing cycle on Azure SQL with Postgres as a shadow comparison.
8. Contract: stop reverse CDC after the day-1 invoicing run reconciles. **Point of no return.**

**4. Dedupe across the move.** The dedupe key is data, not process state: `(tenant_id, external_event_id)` exists on both sides via backfill/CDC before writes move. A retry landing on Azure SQL finds the row (unique index) and returns the stored event. Danger: the collation. If the Azure SQL column is case-insensitive, two distinct Postgres keys collide on the way in (the backfill fails with 2601, or worse, a `NOT EXISTS` backfill silently drops one = under-billing). Pre-check: `SELECT tenant_id, lower(external_event_id), count(*) ... HAVING count(*) > 1` on Postgres.

**5. Verification.** Per tenant/day `COUNT`, `SUM(quantity)`; per invoice `SUM(amount)` and line count; max scale check (`amount <> ROUND(amount, 2)` = 0 rows); key comparison with a binary collation; random-sample row diff (hash of all columns).

**6. Rollback.** Up to step 5: flip the read flag back (seconds). Step 6–7: flip writes back; reverse CDC has kept Postgres current; replay any gap from the Azure SQL `seq` watermark. After step 8: rollback = a new migration project.

**7. Invoicing run.** Freeze: no source switch within 72 h of day 1; the run reads from exactly one database named in its config and records it in the invoice provenance (`source_reference`).

**8. Failure modes.** CDC lag at 3,000/s → back-pressure/alert on lag, never cut over during peak. Backfill blocking ingestion → batch by 5k rows (below lock escalation), low priority, stop on log-rate alarm. Identity collisions → never copy `seq` into an identity column during dual-write; let Azure SQL generate `seq`, keep `id`/`external_event_id` as the identity that matters (or `SET IDENTITY_INSERT` only during backfill, then reseed above max). Timezone bug → `timestamptz` → `datetimeoffset` with offset 0; verify with the per-day checksums, which catch day-boundary shifts.

**Rubric.** Strong = per-table strategy (append-only vs mutable), gated steps with a flag per step, reverse replication for rollback, the collation pre-check, and money/day checksums. Weak = "use Azure DMS and switch the connection string".
