# S2 — reference operating plan: `usage_events` at 100M rows

**Diagnosing the four symptoms.**
- *Fast at 09:00, slow at 17:00 for new tenants* = the ascending-key problem. A new tenant's `tenant_id` and today's `occurred_at` are beyond the last histogram step; the estimate is tiny (on compat ≥ 120 the new cardinality estimator assumes an average density, which is still wrong for a fast-growing tenant). Auto-update on a 100M-row table triggers after about `SQRT(1000 × 100M)` ≈ 316k modifications (compat 130+ dynamic threshold), roughly every hour at 8M/month. Plans compiled on stale stats stay cached.
- *3h40 nightly rebuild* = maintenance by habit. The clustered `seq` index barely fragments (append-only); `ix_usage_events_tenant_occurred` and `ux_usage_events_id` (random GUID) do. Offline rebuilds (Standard) lock the table.
- *Rollup plan flips* = the filtered index's statistics: the filtered stats on `rolled_up = 0` change completely every minute (rows enter and leave), and the auto-update threshold is computed on the **whole table's** modification count, so its stats are almost always stale.
- *60 GB log from retention delete* = row-by-row fully logged delete of ~8M rows in one transaction.

**Plan.**
1. **Statistics:** a job every 30 minutes: `UPDATE STATISTICS billing.usage_events ix_usage_events_unrolled WITH FULLSCAN` (it's small), and hourly `UPDATE STATISTICS ... ix_usage_events_tenant_occurred WITH SAMPLE 5 PERCENT, PERSIST_SAMPLE_PERCENT = ON`. With partitioning: `STATISTICS_INCREMENTAL = ON` and update only the current partition. Consider `AUTO_UPDATE_STATISTICS_ASYNC` so queries don't wait on stats updates.
2. **Index maintenance:** drop the nightly rebuild-all. Measure `avg_fragmentation_in_percent` and page density weekly; reorganize/rebuild only indexes that are large and actually range-scanned. The GUID unique index: fill factor 90, or change `id` to a sequential GUID (UUIDv7 generated in the domain) so inserts append. On Azure SQL / Enterprise: `REBUILD WITH (ONLINE = ON, RESUMABLE = ON, MAX_DURATION = 25 MINUTES)`.
3. **Partitioning:** monthly `RANGE RIGHT` on `occurred_at` → clustered index `(occurred_at, seq)` or keep `seq` and partition on it by ranges that map to months (simpler for append, but retention by time needs a mapping table). Unique indexes must include the partition column to be aligned: `ux_usage_events_tenant_external` becomes non-aligned (keep it as a non-partitioned global index, which blocks `SWITCH`) **or** becomes `(tenant_id, external_event_id, occurred_at)`, which no longer guarantees uniqueness of the external id alone. Resolution: a separate narrow dedupe table `usage_event_keys (tenant_id, external_event_id)` (non-partitioned, unique, purged on the same 13-month retention in batches) and an aligned partitioned event table. Retention: `SWITCH PARTITION` to a staging table + `TRUNCATE`, or `TRUNCATE TABLE ... WITH (PARTITIONS (n))`: metadata-only, no 60 GB log.
4. **Rollups at scale:** a clustered columnstore on an **archive** of closed months (10× compression, batch-mode aggregates for finance reports); keep the hot table rowstore (singleton inserts into columnstore land in the delta store and need tuple-mover work). `usage_daily_rollups` stays rowstore (point upserts from the job).
5. **Monitoring:** Query Store "regressed queries" (plan changes with CPU up), alert on `modification_counter / rows` for the hot indexes, `sys.dm_db_index_usage_stats` to find write-only indexes, `log_reuse_wait_desc`, ingestion p99 SLO dashboard with rollup-job duration overlaid.
6. **Rollout of partitioning live:** create the partitioned table + dedupe table, dual-insert from the app (flag), backfill history in `seq` ranges of 50k rows (keyset, throttled), verify per-day checksums, switch reads, then writes, then rename/drop. Rollback: flags back to the old table, which kept receiving writes until the final step.

**Rubric.** Strong = explains *why* stats go stale (ascending key + threshold), refuses rebuild-all, resolves the "unique index vs aligned partition" conflict explicitly, and uses partition switch/truncate for retention.
