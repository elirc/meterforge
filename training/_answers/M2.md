# M2 — reference answer

**Status:** the index code below was built and scripted with EF Core 10.0.12 (the generated DDL is quoted exactly). All numbers are
**UNVERIFIED expectations**; there was no SQL Server when this was written. Measure them yourself (commands in the ticket and `evidence/README.md`).

## 1. The covering index
```csharp
usage.HasIndex(e => new { e.TenantId, e.OccurredAt })
    .IncludeProperties(e => new { e.SubscriptionId, e.Meter, e.Quantity })
    .HasDatabaseName("ix_usage_events_tenant_occurred_cover")
    .IsCreatedOnline();
```
`dotnet ef migrations script` then shows (offline-verified on the lab branch, 2026-09-24):
`CREATE INDEX [ix_usage_events_tenant_occurred_cover] ON [billing].[usage_events] ([tenant_id], [occurred_at]) INCLUDE ([subscription_id], [meter], [quantity]) WITH (ONLINE = ON);`
- Keys: `tenant_id` (equality) then `occurred_at` (range): equality first, range second. `quantity` is only aggregated, never filtered or sorted, so it goes in `INCLUDE` (leaf level only, smaller upper levels, no key-width limit).
- `ONLINE = ON` requires Enterprise/Developer edition or Azure SQL; on Standard the statement **fails**, so the migration needs an edition check or a separate script for Standard (offline during a window).
- Replace, don't add: the new index makes `ix_usage_events_tenant_occurred` redundant (same keys, it's a prefix). Drop it in a **later** migration, after checking `sys.dm_db_index_usage_stats` shows no other reader.

**Expected effect:** tenant-0001: Index Seek, **no Key Lookup**, single-digit logical reads. Whale: Index Seek with a range scan over its week only
(~115k narrow rows ≈ 1–2k pages instead of the whole table). Both plans are now the same shape, so which tenant compiles first no longer matters.

## 2. Can `EF.Constant` go?
Yes, **after** the covering index, and not before. Evidence to collect (4 runs of `SqlLab bench-sniff`):

| Build | `--first tenant-whale` small-tenant p50 | `--first tenant-0001` small-tenant p50 |
|---|---|---|
| parameterized, old index | high (scan plan reused) | low, but whale suffers (lookup plan reused) |
| parameterized, covering index | low | low |

That table **is** the argument to the DBA: plan reuse is safe once the plan is value-independent. Alternatives and their costs:
`OPTION (RECOMPILE)` (compile CPU on every call, no plan-cache stats), `OPTIMIZE FOR UNKNOWN` (average plan, stable but mediocre),
`EF.Constant` (plan-cache bloat, 1 plan per tenant, compile per new tenant), PSP optimization at compat 160 (automatic variants, limited to
qualifying equality predicates), Query Store plan forcing (pins one plan, still wrong for one side).

## 3. Filtered index
The rollup SQL uses the literal `rolled_up = 0`, which matches the filter `[rolled_up] = 0`, so the plan can use `ix_usage_events_unrolled`
(expected: Index Seek on `occurred_at < @cutoff`). Variants that silently stop using it:
- `WHERE rolled_up = @flag` (EF `Where(e => e.RolledUp == flag)` with a variable): the cached plan must be valid for `@flag = 1` too, so the filtered index can't be used (unless `OPTION (RECOMPILE)`).
- `WHERE rolled_up <> 1`: logically the same for a `bit NOT NULL`, but the optimizer doesn't prove `<> 1` ⊆ `= 0` for filtered-index matching in all cases; check the plan rather than assume.
- A `SET ANSI_NULLS OFF`/`QUOTED_IDENTIFIER OFF` session: filtered indexes require the right SET options, or inserts fail and queries ignore the index.

## Write cost
One more nonclustered index maintained per insert (one extra B-tree insert + log record, ~60 bytes per row for this index).
Measure: `SqlLab soak --seconds 60 --batch 1` inserts/s and `sys.dm_db_index_operational_stats` leaf inserts/latch waits before vs after.
Expect a few percent on the insert path; the lookup savings on reads are orders of magnitude.

**Rubric.** Strong = INCLUDE reasoning + edition caveat for ONLINE + the 2×2 sniffing table (or its plan) + one filtered-index trap shown in a plan.
