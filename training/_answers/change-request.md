# Sealed reference placement — usage caps

1. **Placement.** Rule in the domain: extend `Domain/Entitlements/Entitlements.cs` (`EntitlementEvaluator` already answers "requested within included quantity?"), or add a small `UsageCap` value type next to it. The check belongs in `Application/Usage/UsageIngestionService.IngestAsync`, **after** the replay lookup (replays are never re-checked) and **before** insert. Storage behind a new port `IUsageCapStore` (Application) with in-memory and SQL Server adapters. `EntitlementEndpoints` stays a calculator; don't route ingestion through it.
2. **Data.** `billing.usage_caps (tenant_id, subscription_id, meter, period_start, cap_quantity)` and a counter `billing.usage_cap_counters (tenant_id, subscription_id, meter, period_start, consumed)` PK on all four. Raw `usage_events` sums are too slow per insert; `usage_daily_rollups` lags by the job interval, so it can't enforce a hard cap.
3. **Concurrency.** One atomic conditional update in the same transaction as the event insert: `UPDATE usage_cap_counters SET consumed = consumed + @q WHERE ... AND consumed + @q <= cap` → 0 rows = reject. The row lock serializes the 40 servers for that one subscription/meter: throughput per subscription is bounded by that row (fine for a cap feature; document it). Lock order must match the rollup job (events → counters, or put the counter update first everywhere) or you rebuild incident 002. Only capped subscriptions pay this cost.
4. **Replays.** Accepted: the replay check runs first and returns the stored event (it was already counted).
5. **Contract.** `422` with `code = "usage.cap_reached"` fits the existing Problem Details convention (`BusinessRuleExceptionHandler`); `429` is arguably better for "stop calling" and needs `Retry-After` = next period start. Adding a new error code is backward-compatible in V1 if clients treat unknown codes as failures; document it.
6. **Webhooks.** Threshold crossings detected in the same transaction (old consumed < 80% ≤ new consumed) write one `outbox_messages` row with a deterministic id = hash(tenant, sub, meter, period, threshold), so the PK makes it exactly-once per period. A publisher (new) delivers it. Links: 01 outbox (apprenticeship page `01-transactional-outbox`, not in this repo), 02 idempotency (apprenticeship page `02-idempotency`, not in this repo).
7. **Tests.** Domain: cap arithmetic, boundaries (exactly at cap, fractional quantities). Application: replay after cap, reject over cap. SQL Server integration: 40 parallel ingests with 10 units left → exactly 10 accepted; outbox has exactly one 100% row. Plus a soak run with the rollup job to check for 1205s.

**Rubric.** Strong placement names the ingestion service + a port (not the calculator endpoint), rejects rollups as the enforcement source, gives an atomic conditional update, and notices lock ordering with the rollup job.
