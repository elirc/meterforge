# J1 — reference answer

**Explain-before-touching**
1. `src/MeterForge.Api/Program.cs` on the lab branch: `if (useSqlServer) builder.Services.AddMeterForgeSqlServer(sqlServerConnection!)`, right after the in-memory registrations. `SqlServerRegistration.AddMeterForgeSqlServer` calls `services.RemoveAll<IUsageEventStore>()` and re-registers it scoped. Order matters: if the SQL Server call ran first, the later `AddSingleton<IUsageEventStore, InMemoryUsageEventStore>` would win (last registration wins for single resolution).
2. `UsageEndpoints` (minimal API lambda) → `UsageIngestionService.IngestAsync` → `SqlServerUsageEventStore.FindByExternalIdAsync` / `AddAsync` → `MeterForgeDbContext` → SqlClient → `billing.usage_events`.
3. 2601 = duplicate key in a unique **index**, 2627 = duplicate key in a unique/PK **constraint**. Here: `ux_usage_events_tenant_external`. You see it when two deliveries of the same event (SDK retry while the first attempt is still in flight, or two SDK instances) both pass `FindByExternalIdAsync` before either commits. The index is the real guarantee; the lookup is an optimization.
4. `tenant_id`, `meter`, `external_event_id`, `currency`, `event_type`, `source_reference` are `varchar` (`IsUnicode(false)`); `description`, `subject`, `payload` are `nvarchar`. It matters because: (a) half the storage and index size; (b) if any code sends an `nvarchar` parameter against a `varchar` column, SQL Server converts the **column** (`CONVERT_IMPLICIT`) and can't seek (incident 003); (c) tenant ids must then be ASCII by contract.
5. `DbContext` is not thread-safe and holds a change tracker and a connection; a singleton would be shared by concurrent requests (and would grow forever). `AddDbContext` registers the context as scoped, so anything depending on it must be scoped too. A singleton capturing a scoped service is a "captive dependency" (ASP.NET Core throws for it in Development via scope validation).

**The 5-line note (model).** `seq` is an ever-increasing `bigint IDENTITY` used as the clustered key, so inserts append to the last page
of the table instead of splitting random pages. `id` is a random GUID generated in the domain (`Guid.NewGuid()`); as a clustered key it
would scatter 400+ inserts/s across the whole table, fragment it, and make every nonclustered index carry a 16-byte key instead of 8.
`id` stays unique (`ux_usage_events_id`) for lookups by id. Cost: that unique GUID index still takes random inserts (see S2).
