**Explain-before-touching**
1. `tenant_id` is a literal (`'tenant-0001'`) because of `EF.Constant`; `@from` and `@to` are `datetimeoffset` parameters.
2. `ix_usage_events_tenant_occurred (tenant_id, occurred_at)` can seek on tenant + range. It doesn't contain `subscription_id`, `meter`, `quantity`, so every matching row needs a lookup into the clustered index (`seq`). (Nonclustered index rows carry the clustering key `seq`, which is how the lookup finds the row.)
3. A Key Lookup is one clustered-index seek (root → leaf, ~3–4 page reads) **per matching row**, executed by a Nested Loops join. Cost is proportional to matching rows, not table size, so it's great for 50 rows and terrible for 115k.
4. The estimated plan is what the optimizer planned; the actual plan adds runtime counters (actual rows, executions, per-operator reads/time with `STATISTICS XML`). You need actuals to see estimate-vs-actual gaps and the real number of lookups.

**Why the plans differ, and EF.Constant's role (model 3 sentences).** With the tenant inlined as a literal, SQL Server compiles and caches a
separate plan per tenant, each costed for that tenant's row count from the `tenant_id` histogram. For a small tenant, seek + ~50 lookups is
cheapest; for the whale, 115k random lookups would cost more than reading the whole table sequentially, so it scans. If the tenant were a
parameter, one cached plan would serve both, built for whichever tenant compiled it first (INC-001 is exactly that).
